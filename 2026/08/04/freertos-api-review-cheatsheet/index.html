FreeRTOS 复习速查：任务、队列、信号量与常用 API

afterTvT 发布于 2026-08-04

  • 📒 技术笔记
  • 🏷️ 嵌入式
  • 🏷️ FreeRTOS
  • 🏷️ STM32
  • 🏷️ RTOS

这篇笔记给自己复习 FreeRTOS 和快速查 API 用。重点不是完整讲操作系统原理，而是把常用功能浓缩成：它解决什么问题、常用在哪、API 怎么查、工程里容易踩什么坑。

本文按 Classic FreeRTOS 的常见 API 编写，具体可用项仍取决于内核版本、移植层和 FreeRTOSConfig.h。查 API 时先确认三个问题：调用者是任务还是 ISR、这个对象是否允许阻塞、数据的所有权由谁负责。

FreeRTOS 的核心思路可以先记成一句话：把一个复杂的 while (1) 拆成多个任务，再用队列、信号量、互斥锁、事件组和通知把任务之间的关系说清楚。

一、FreeRTOS 最小心智模型

概念 一句话理解 常用在哪
Task 任务 一个独立执行的函数，通常死循环运行 传感器采样、通信解析、控制算法、UI 刷新
Priority 优先级 数字越大越容易先运行 中断后处理、控制环、通信任务分级
Tick RTOS 的系统节拍 延时、超时、软件定时器
Scheduler 调度器 决定当前哪个任务运行 所有任务切换的核心
Block 阻塞 任务主动等待事件，CPU 让给别人 等队列、等信号量、延时
ISR 硬件中断服务函数 串口接收、DMA 完成、定时器中断

最常见的工程结构：

不要把 FreeRTOS 理解成“用了就一定实时”。实时性来自合理的优先级、短中断、少阻塞、可预测的临界区和明确的数据流。

先记住四条边界：普通 API 只在任务上下文使用；ISR 只用对应的 FromISR API；Mutex 只能由持有它的任务释放；通知、队列和事件组解决的是不同层次的问题，不能只看函数名相似就互换。

API 返回值速记

返回形式 典型 API 重点
NULL / pdPASS xTaskCreate()、xQueueCreate() 创建失败要立刻处理
pdTRUE / pdFALSE 或 pdPASS / pdFAIL 队列、信号量、通知 超时、队列满、服务队列满都可能失败
EventBits_t xEventGroupWaitBits() 返回实际满足的 bit，不能只看是否返回
size_t Stream/Message Buffer 收发 返回实际收发的字节数，可能小于请求值

不要把“函数返回了”当成“操作成功了”。尤其是 ISR 发送、定时器命令和带超时的等待，都要按返回值设计丢包、重试或错误恢复策略。

二、任务 Task

常用 API

API 作用 速记
xTaskCreate() 动态创建任务 栈从 heap 分配
xTaskCreateStatic() 静态创建任务 栈和 TCB 自己提供
vTaskDelete() 删除任务 删除自己传 NULL
vTaskDelay() 延时一段 tick 相对延时
vTaskDelayUntil() 固定周期运行 控制环、采样周期更常用
uxTaskPriorityGet() 获取任务优先级 调试和状态监控
vTaskPrioritySet() 修改任务优先级 少用，容易让系统难分析
xTaskGetTickCount() 获取当前 tick 软计时、超时判断
uxTaskGetStackHighWaterMark() 查看任务栈余量 排查栈是否太小

最小任务模板：

常用在哪

  • 一个周期性动作一个任务：传感器采样、LED 状态、按键扫描。
  • 一个阻塞等待源一个任务：串口协议、CAN 接收、网络收包。
  • 一个复杂业务状态机一个任务：控制模式切换、上位机命令处理。

注意点

  • 任务函数不要 return，通常写 for (;;)。
  • 检查 xTaskCreate() 的返回值；失败通常表示 heap 不够，失败后不能继续假设任务句柄有效。
  • 删除动态任务后，相关内存由 Idle 任务异步回收；不要频繁创建/删除来实现周期工作，也不要依赖“删除后立即释放”。静态任务的缓冲区由应用自己管理。
  • vTaskDelay() 是相对延时，任务执行时间会叠加进周期；固定周期优先用 vTaskDelayUntil()。
  • vTaskDelayUntil() 只负责维持唤醒节拍；如果一次执行已经超过周期，它可能立即返回，不会替你补跑或恢复控制算法的实时性。
  • 栈大小的单位是 StackType_t，通常是 word，不是字节；数组、printf、递归、复杂局部变量都会吃栈，uxTaskGetStackHighWaterMark() 返回的余量也通常是 word。
  • 优先级不要乱堆高。高优先级任务如果不阻塞，会饿死低优先级任务。

固定周期模板：

三、调度、延时和优先级

API / 宏 作用
vTaskStartScheduler() 启动调度器
taskYIELD() 当前任务主动让出 CPU
vTaskSuspend() 挂起任务
vTaskResume() 恢复任务
pdMS_TO_TICKS(ms) 毫秒转 tick
portMAX_DELAY 最大等待时间；开启挂起管理时才可表示无限等待

优先级可以按场景粗分：

类型 优先级建议 例子
中断后处理 较高 DMA 完成后解析一帧关键数据
控制或采样 中高 1 ms 控制任务、IMU 融合
通信协议 中等 串口命令、CAN 报文处理
日志和显示 低 OLED、printf、文件写入
空闲后台 最低 清理、统计、低功耗入口

注意：FreeRTOS 的数值越大优先级越高，最大值受 configMAX_PRIORITIES 限制。

taskYIELD() 主要用于让出给同优先级的就绪任务；它不是让低优先级任务插队。vTaskSuspend()/vTaskResume() 是强制挂起/恢复，不适合作为可靠的事件同步，尤其不要用 vTaskResume() 代替 ISR 到任务的通知，因为事件可能在任务挂起前发生而被丢失。

pdMS_TO_TICKS() 的结果受 TickType_t 宽度和 tick 频率限制，超长毫秒数可能溢出。需要做超时判断时，优先使用 FreeRTOS 的 tick 差值或 TimeOut_t 机制，不要直接用有符号整数比较绝对 tick 值。

四、队列 Queue

队列用于“传数据”，可以在任务之间传结构体、指针或固定长度消息。它自带阻塞等待，非常适合生产者-消费者模型。

常用 API

API 作用 场景
xQueueCreate() 创建队列 动态创建
xQueueCreateStatic() 静态创建队列 不想依赖 heap
xQueueSend() 发送到队尾 普通生产者
xQueueSendToFront() 发送到队头 紧急消息插队
xQueueReceive() 接收并移除消息 消费者
xQueuePeek() 读取但不移除 观察当前消息
uxQueueMessagesWaiting() 当前消息数 调试、限流
xQueueReset() 清空队列 状态切换、错误恢复
xQueueSendFromISR() 中断里发送 ISR 到任务

例子：

常用在哪

  • 串口接收任务把完整帧发给协议任务。
  • 采样任务把传感器数据发给控制任务。
  • 多个模块把日志消息发给低优先级打印任务。

注意点

  • 队列复制的是固定大小数据。大结构体频繁复制会浪费时间，必要时传指针。
  • 传指针时要保证指向的数据生命周期有效，不能指向马上失效的局部变量。
  • xQueueSend()/xQueueReceive() 的阻塞时间是等待队列状态变化的最长时间，不是整个处理流程的超时；必须检查返回值。
  • 中断里必须用 FromISR 版本，并在需要时请求任务切换。队列满时 ISR 发送会失败，不能把它当成可靠的无限缓存。
  • 只保留“最新值”时，可以考虑长度为 1 的队列配合 xQueueOverwrite()；它不是普通 FIFO，不能用来保存多条消息。

ISR 发送模板：

五、信号量 Semaphore

信号量更适合“通知事件”或“资源计数”，不适合传复杂数据。

二值信号量

API 作用
xSemaphoreCreateBinary() 创建二值信号量
xSemaphoreGive() 释放 / 通知
xSemaphoreTake() 获取 / 等待
xSemaphoreGiveFromISR() 中断里通知

常用场景：DMA 完成、串口空闲中断、按键事件、外部中断唤醒任务。

二值信号量只有“有/无”状态：连续多次 give 不会累积成多次事件。若每一次事件都必须保留，用计数信号量、队列或带计数的任务通知。

计数信号量

API 作用
xSemaphoreCreateCounting() 创建计数信号量
uxSemaphoreGetCount() 查看当前计数

常用场景：资源池、多个相同事件累计、固定数量 buffer 管理。

注意：如果事件本身带数据，用队列更清楚；如果只是“来了几次”，计数信号量合适。

信号量没有资源所有权语义，也没有优先级继承；它适合同步和计数，不适合保护共享外设。

六、互斥锁 Mutex

互斥锁用于保护共享资源。它和二值信号量长得像，但语义不同：Mutex 有优先级继承，更适合资源互斥。

常用 API

API 作用
xSemaphoreCreateMutex() 创建普通互斥锁
xSemaphoreCreateRecursiveMutex() 创建递归互斥锁
xSemaphoreTake() 加锁
xSemaphoreGive() 解锁
xSemaphoreTakeRecursive() 递归加锁
xSemaphoreGiveRecursive() 递归解锁

常用场景：

  • 多任务共用 UART 打印。
  • 多任务访问同一个 I2C/SPI 总线。
  • 文件系统、Flash 写入、共享状态结构体。

注意点：

  • Mutex 不能在 ISR 中使用。
  • 谁 take，谁 give，不要跨任务释放普通互斥锁。
  • 加锁范围越短越好，不要拿着锁做长时间延时。
  • 保护共享资源用 Mutex，不要用二值信号量硬凑。
  • 递归 Mutex 只有在同一任务确实需要嵌套获取时才使用；它会掩盖调用层级混乱，且必须按获取次数逐次 give。
  • 优先级继承只能缓解“低优先级任务持锁、高优先级任务等待”的优先级反转，不能解决死锁、锁顺序错误或锁内长时间阻塞；锁的层级和持有时间仍要从架构上约束。

七、任务通知 Task Notification

任务通知是 FreeRTOS 里非常轻量的任务唤醒/计数/传值机制。很多“一对一通知”可以不用信号量或队列。

常用 API

API 作用
xTaskNotifyGive() 给任务一个通知计数
ulTaskNotifyTake() 等待并消耗通知计数
xTaskNotify() 带动作地设置通知值
xTaskNotifyWait() 等待通知值
xTaskNotifyFromISR() ISR 中通知
vTaskNotifyGiveFromISR() ISR 中给通知计数

常用场景：

  • DMA 完成后唤醒唯一处理任务。
  • 定时器中断唤醒控制任务。
  • 一个任务给另一个任务传一个 32 位标志或数值。

ulTaskNotifyTake(pdTRUE, ...) 会在成功唤醒后清零通知计数；传 pdFALSE 则通常只消费一个计数。xTaskNotifyWait() 还要分别理解 ulBitsToClearOnEntry 和 ulBitsToClearOnExit，否则很容易出现重复处理或丢 bit。

任务通知通常是一对一的，每个任务默认有 notification index 0；需要多个独立通知槽时要打开通知数组配置并使用 ...Indexed() API。创建任务后再把句柄交给 ISR，并在此之前启用中断，否则 ISR 可能使用空句柄。多个生产者、多条不同消息、复杂数据流，队列或事件组会更清楚。

八、事件组 Event Group

事件组适合多个 bit 表示多个事件，任务可以等其中一个 bit 或一组 bit。

常用 API

API 作用
xEventGroupCreate() 创建事件组
xEventGroupSetBits() 设置事件位
xEventGroupClearBits() 清除事件位
xEventGroupWaitBits() 等待事件位
xEventGroupGetBits() 获取当前事件位
xEventGroupSetBitsFromISR() ISR 中设置事件位

常用场景：

  • 等待系统初始化完成：IMU、Flash、通信都 ready。
  • 通信状态标志：连接、认证、收到配置、允许上报。
  • 一个任务同时等待多个事件源。

注意：事件组只表达“状态/事件位”，不携带详细数据。需要数据就配合队列。

xEventGroupWaitBits() 要同时看 xClearOnExit、xWaitForAllBits 和返回值；超时返回时可能只拿到部分 bit。事件组的可用 bit 数还受端口和内核控制位占用影响，不要默认所有 32 位都能给应用使用。

xEventGroupSetBitsFromISR() 不是在 ISR 里直接完成置位，而是把操作发送给 timer/daemon task；服务队列满时可能失败。因此它适合低频状态通知，不适合要求 ISR 立即完成的路径，快速唤醒通常优先用任务通知或二值信号量。

九、软件定时器 Timer

软件定时器由 FreeRTOS 的 timer task 回调执行，不是硬件定时器中断。

常用 API

API 作用
xTimerCreate() 创建软件定时器
xTimerStart() 启动
xTimerStop() 停止
xTimerReset() 重置计时
xTimerChangePeriod() 修改周期
xTimerStartFromISR() ISR 中启动

常用场景：

  • 按键消抖超时。
  • 通信心跳、连接超时。
  • 低频状态灯闪烁。
  • 不要求硬实时的周期动作。

注意：定时器回调运行在 timer task 里，不要在回调里长时间阻塞，否则会影响其他软件定时器。

回调中不要调用可能阻塞的 API，也不要做长时间计算；需要复杂处理时只发送通知/队列消息，让专用任务完成。xTimerStart()、xTimerStartFromISR() 等操作通过 timer command queue 排队，调用者应检查返回值，并合理配置 configTIMER_QUEUE_LENGTH、configTIMER_TASK_PRIORITY 和 timer task 栈大小。

十、Stream Buffer 和 Message Buffer

这两个常用于字节流和变长消息，比队列更适合串口、网络这类数据流。

类型 适合数据 常用场景
Stream Buffer 连续字节流 UART RX、日志流、网络流
Message Buffer 一条条变长消息 协议包、命令帧

常用 API：

API 作用
xStreamBufferCreate() 创建 stream buffer
xStreamBufferSend() 写入字节流
xStreamBufferReceive() 读取字节流
xStreamBufferSendFromISR() ISR 中写入
xMessageBufferCreate() 创建 message buffer
xMessageBufferSend() 写入一条消息
xMessageBufferReceive() 读取一条消息

注意：典型用法是一写一读。多写多读要额外加锁或重新设计数据流。

Stream Buffer 不保留消息边界，xStreamBufferReceive() 可能只返回半帧；“收到几个字节就唤醒”也不等于收到了一个完整协议包。Message Buffer 会保留消息边界，但消息长度还受缓冲区容量限制；ISR 发送同样必须检查实际写入/发送的字节数或结果。

十一、内存管理和 Heap

FreeRTOS 常见动态对象包括任务、队列、信号量、定时器。它们通常从 FreeRTOS heap 里分配，不一定等同于 C 标准库 malloc()。

常用 API

API / Hook 作用
pvPortMalloc() FreeRTOS 分配内存
vPortFree() FreeRTOS 释放内存
xPortGetFreeHeapSize() 当前剩余 heap
xPortGetMinimumEverFreeHeapSize() 历史最低剩余 heap
vApplicationMallocFailedHook() 分配失败钩子

常见 heap 实现：

文件 特点
heap_1.c 只分配不释放
heap_2.c 可释放但不合并碎片
heap_3.c 包装标准库 malloc/free
heap_4.c 可释放并合并相邻空闲块，常用
heap_5.c 支持多个非连续内存区

注意点：

  • 嵌入式项目里尽量在初始化阶段创建对象，运行中少动态创建删除。
  • 打开 configUSE_MALLOC_FAILED_HOOK，分配失败要能停住并定位。
  • xPortGetFreeHeapSize() 只统计 FreeRTOS heap；如果工程还调用 C 库 malloc()，两者的余量不是同一个指标。
  • configSUPPORT_DYNAMIC_ALLOCATION 和 configSUPPORT_STATIC_ALLOCATION 决定哪些创建 API 可用；静态对象不会从 FreeRTOS heap 扣除，但其 TCB/栈缓冲区必须长期有效且满足对齐要求。
  • 栈溢出和 heap 不够是 FreeRTOS 初学阶段最高频问题。

十二、临界区和中断安全

常用 API

API 作用
taskENTER_CRITICAL() 进入任务级临界区
taskEXIT_CRITICAL() 退出任务级临界区
taskENTER_CRITICAL_FROM_ISR() ISR 中进入临界区
taskEXIT_CRITICAL_FROM_ISR() ISR 中退出临界区
vTaskSuspendAll() 暂停调度器
xTaskResumeAll() 恢复调度器

常用场景：

  • 保护很短的共享变量读改写。
  • 修改链表、状态位、硬件寄存器组合配置。
  • 防止任务切换造成中间状态被读取。

注意点：

  • 临界区越短越好，里面不要调用可能阻塞的 API。
  • 暂停调度器不等于关中断，中断仍然会来。
  • ISR 中只能调用带 FromISR 的 FreeRTOS API。
  • 临界区不是通用锁；它会影响中断响应。跨任务共享资源仍应使用 Mutex，原子变量或短临界区只解决很小的读改写。

十三、FreeRTOSConfig.h 必查项

配置 作用 建议
configCPU_CLOCK_HZ CPU 时钟 和系统时钟一致
configTICK_RATE_HZ tick 频率 常见 1000 Hz 或 100 Hz
configMAX_PRIORITIES 最大优先级数量 别开太少，也别滥用
configMINIMAL_STACK_SIZE 最小任务栈 单位注意是 word
configTOTAL_HEAP_SIZE FreeRTOS heap 大小 根据任务和队列估算
configUSE_PREEMPTION 是否抢占式调度 常用 1
configUSE_TIME_SLICING 同优先级时间片 多数项目可开
configUSE_MUTEXES 启用互斥锁 用 Mutex 必开
configUSE_TIMERS 启用软件定时器 用 Timer 必开
configTIMER_TASK_PRIORITY timer task 优先级 要能及时处理 timer command
configTIMER_QUEUE_LENGTH timer command queue 长度 根据 ISR/任务提交频率估算
configTIMER_TASK_STACK_DEPTH timer task 栈深度 回调复杂时适当增大
configCHECK_FOR_STACK_OVERFLOW 栈溢出检测 调试期建议 2，具体能力取决于 port
configUSE_MALLOC_FAILED_HOOK 分配失败 hook 建议开
configUSE_TRACE_FACILITY 任务统计/调试信息 使用任务列表时打开
configASSERT() 断言 必须定义成能停住

中断相关还必须查 configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY（CMSIS 优先级表示）或 configMAX_SYSCALL_INTERRUPT_PRIORITY（移位后的端口表示）。以 CMSIS 的优先级数值为例，只有数值大于等于 configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 的 ISR 才能调用 FromISR API；数值更小代表硬件抢占优先级更高，不能调用。这个规则最容易配反。启用 configASSERT() 后，FreeRTOS 的中断优先级校验能尽早暴露这类错误。

xTimerStartFromISR() 中断启动软件定时器

注意：portYIELD_FROM_ISR() 的名字在不同移植层可能略有差异，以当前工程 port 为准。

xEventGroupSetBitsFromISR() 和 xTimerStartFromISR() 还依赖 timer/daemon task 的命令队列，返回失败时不能假设操作已经完成。Cortex-M 工程尤其要确认 NVIC 优先级分组、实际抢占优先级，以及 ISR 是否落在可调用 FreeRTOS API 的范围内。

十六、调试和排错清单

现象 优先检查
vTaskStartScheduler() 后没跑 heap 不够、任务创建失败、中断优先级配置错误
任务偶发 HardFault 栈溢出、野指针、ISR 调了非 FromISR API
低优先级任务不运行 高优先级任务没有阻塞或延时
队列一直满 消费任务优先级太低、处理太慢、队列长度太小
队列一直空 生产者没发送、超时太短、句柄没初始化
Mutex 死锁 忘记 give、重复加锁、锁内阻塞
延时不准 tick 配置、系统时钟、临界区太长、中断关闭太久
定时器回调卡住 timer task 优先级低、回调里阻塞太久
内存越来越少 动态创建删除、未释放、heap 碎片

十七、快速背诵版

  • 任务负责执行，队列负责传数据，信号量负责通知，Mutex 负责保护资源。
  • ISR 里只用 FromISR API，并用 portYIELD_FROM_ISR() 触发必要的任务切换。
  • 高优先级任务必须经常阻塞，否则低优先级任务没有机会运行。
  • 周期任务用 vTaskDelayUntil()，简单延时才用 vTaskDelay()。
  • 共享外设用 Mutex，ISR 到任务用通知或二值信号量。
  • 大数据不要在队列里反复复制，传指针时要保证生命周期。
  • 打开栈溢出检测、malloc 失败 hook 和 configASSERT()。
  • 调试先看任务栈余量、heap 余量、队列深度和中断优先级。
  • 看到“偶发”问题，先确认所有创建 API、队列发送、信号量获取和 ISR 发送的返回值，再查栈水位和中断优先级。

真正写工程时，API 细节以当前 FreeRTOS 版本和移植层为准；STM32 工程还要特别注意 NVIC 优先级分组、configMAX_SYSCALL_INTERRUPT_PRIORITY / configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY、可调用 FreeRTOS API 的中断范围，以及 CubeMX 生成配置是否和 FreeRTOSConfig.h 一致。
