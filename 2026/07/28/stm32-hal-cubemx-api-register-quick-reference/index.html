STM32 HAL 库常用 API 速查：配合 CubeMX 理解外设与寄存器

这篇笔记主要服务于两个场景：平时使用 CubeMX 配置 STM32 外设时，能够快速找到常用 HAL API；面试复习时，能够说明 HAL API 背后大致修改了哪些寄存器，以及 HAL、LL 和直接寄存器操作之间的关系。这里不追求把每个函数都罗列出来，而是优先整理高频 API、调用套路和容易出错的地方。

不同 STM32 系列的 HAL 函数和寄存器可能存在差异。本文以常见 STM32 HAL 使用方式为主，具体寄存器名称要以当前芯片的参考手册和对应 HAL 源码为准。

一、CubeMX 和 HAL 的关系

使用 CubeMX 时，通常不是从零手写外设初始化，而是先在 .ioc 工程中完成配置，再由 CubeMX 生成初始化代码。

flowchart LR
  A[CubeMX 配置时钟和外设] --> B[生成 HAL 初始化代码]
  B --> C[main 中调用 MX_xxx_Init]
  C --> D[调用 HAL 阻塞/中断/DMA API]
  D --> E[回调函数处理数据]
  E --> F[业务逻辑和控制算法]

代码 主要作用
HAL_Init() 初始化 HAL、配置 SysTick、设置中断优先级分组
SystemClock_Config() 配置系统时钟、总线时钟和外设时钟来源
MX_xxx_Init() 根据 CubeMX 配置初始化具体外设
HAL_xxx_xxx() 运行期间启动、停止、收发或读取外设
HAL_xxx_MspInit() 配置 GPIO、时钟、DMA 和 NVIC 等底层资源

CubeMX 生成代码中的 USER CODE BEGIN 和 USER CODE END 区域可以修改。其他生成区域可能在重新生成代码时被覆盖，因此自己的变量、函数和业务代码应尽量放在用户代码区域或独立的 .c/.h 文件中。

2. 三种运行方式

方式 特点 常见 API 后缀 适合场景
阻塞 CPU 等待操作结束 无后缀 调试、低速、简单流程
中断 硬件完成后进入回调 _IT 不希望 CPU 一直等待
DMA DMA 自动搬运数据 _DMA 连续采样、批量收发、高吞吐

中断和 DMA 方式通常不是调用函数就结束了，而是要继续准备回调、缓冲区和中断处理函数。

三、GPIO API 速查

API 作用 底层理解
HAL_GPIO_Init() 配置 GPIO 模式、速度、上下拉和复用 修改模式、类型、速度、上下拉、复用寄存器
HAL_GPIO_DeInit() 恢复 GPIO 默认状态 关闭或恢复相关配置
HAL_GPIO_WritePin() 输出高低电平 通常操作 BSRR
HAL_GPIO_ReadPin() 读取输入电平 通常读取 IDR
HAL_GPIO_TogglePin() 翻转输出电平 通常读改写输出寄存器
HAL_GPIO_LockPin() 锁定 GPIO 配置 设置锁定寄存器

CubeMX 中需要确认：GPIO 时钟、模式、输出类型、上下拉、速度、默认电平以及复用功能。GPIO 输出高低电平和 GPIO 初始化是两件事，初始化完成后还要使用 WritePin() 或其他输出 API 改变电平。

四、RCC、时钟和 SysTick

API 作用
HAL_RCC_OscConfig() 配置振荡器、PLL 等时钟源
HAL_RCC_ClockConfig() 配置系统时钟和总线分频
HAL_RCC_GetSysClockFreq() 获取系统时钟频率
HAL_RCC_GetHCLKFreq() 获取 HCLK 频率
HAL_GetTick() 获取 HAL 的毫秒计数
HAL_Delay() 基于 HAL Tick 的毫秒延时

时钟问题是外设异常的高频原因。UART 波特率、定时器频率、ADC 时钟和 USB 时钟都依赖时钟树。

特别注意：某些 STM32 系列中，当 APB 总线预分频不为 1 时，定时器时钟可能是 APB 时钟的两倍。因此定时器频率不能只看 CubeMX 界面上的 APB 频率。

HAL_Delay() 适合简单的主循环延时，不适合放在高频中断中，也不适合代替精确的定时器调度。

五、UART API 速查

API 作用 常见用途
HAL_UART_Init() 初始化 UART 设置波特率、数据位、停止位、校验等
HAL_UART_Transmit() 阻塞发送 调试打印、低速简单发送
HAL_UART_Receive() 阻塞接收 接收固定长度数据
HAL_UART_Transmit_IT() 中断发送 非阻塞发送
HAL_UART_Receive_IT() 中断接收 固定长度或状态机接收
HAL_UART_Transmit_DMA() DMA 发送 批量或连续发送
HAL_UART_Receive_DMA() DMA 接收 连续数据流接收
HAL_UART_IRQHandler() UART 中断处理 在对应 IRQHandler 中调用
HAL_UART_Abort() 中止当前操作 超时、异常恢复
HAL_UART_DeInit() 反初始化 关闭或重新配置 UART

十、HAL API 到寄存器的理解方式

不要把 HAL 理解成“隐藏了所有硬件细节”。更准确的说法是：HAL 把寄存器配置、状态管理、错误处理、中断和 DMA 流程封装成了统一接口。

十二、HAL、LL 和直接寄存器操作

方式 特点 适合场景
HAL 接口统一，CubeMX 集成好，易维护 普通项目、快速开发
LL 更接近寄存器，开销较小 对时序和性能更敏感的部分
直接寄存器 控制最直接，但移植和维护成本高 学习底层、特殊时序、极限优化

比较好的学习路线是：先用 CubeMX 生成 HAL 工程并验证功能，再查看 HAL 源码理解寄存器，最后只在确实需要时使用 LL 或寄存器操作。工程中不建议为了“显得底层”而全部放弃 HAL。

十三、CubeMX 和 HAL 常见坑

  • 重新生成代码后，非用户代码区域可能被覆盖。
  • GPIO、DMA、UART 等外设时钟没有打开，外设自然无法工作。
  • GPIO 复用功能错误，导致 UART、SPI 或定时器引脚没有输出。
  • 定时器时钟受 APB 分频影响，实际频率和直觉不一定相同。
  • 中断服务函数没有调用对应的 HAL_xxx_IRQHandler()。
  • 中断或 DMA 接收完成后，没有重新启动下一次接收。
  • 回调函数名称或参数写错，导致回调根本没有被调用。
  • 在中断回调中使用 HAL_Delay() 或长时间阻塞函数。
  • DMA 缓冲区生命周期不够长，或者长度和数据宽度配置不一致。
  • I2C 地址、上拉电阻、SPI 模式和片选时序配置错误。
  • 只检查函数返回值，不检查 HAL_xxx_GetError() 或外设状态。
  • 直接改寄存器后继续调用 HAL，造成软件状态和硬件状态不一致。
